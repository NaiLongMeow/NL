# NL 架构

> 状态：各端已有项目骨架，功能尚未实现。本文描述已经定下的方向，具体接口会随实现补充。

NL 是一个开源的分布式 agent harness。它可编程，但核心优化方向是陪伴与娱乐：同一个角色可以同时出现在桌面、手机和物联网设备上，并在这些设备之间共享记忆、存储和算力。

## 设计原则

- **协议优先**：各端只通过同一套协议和能力声明对接，任何一端都可以单独替换或重写。
- **轻重分离**：单片机只做传感、执行和音频收发；LLM 推理、语音识别与合成、长期存储、子代理等重活交给算力更强的节点。
- **节点对等**：桌面、云端都运行同一个 `nl-node`，按声明的能力分工，而不是按设备类型写死角色。
- **隐私默认开启**：节点之间端到端加密，走中继时网关也看不到对话内容；API key 只保存在网关，永远不下发到设备。
- **对 agent 友好的工具链**：本项目主要由 agent 编写，选型优先看工具链能否在命令行里稳定地搭建、构建和测试，而不是人工维护成本。

## 整体结构

```
                    ┌──────────────────────────────┐
                    │ 云端总网关                    │

```

## 各端技术栈

### 共享核心（Rust）

| 模块 | 职责 |
|---|---|
| `nl-proto` | Protobuf 定义的消息格式，支持 `no_std`，单片机也能使用 |
| `nl-transport` | 连接建立与传输抽象（见下文“连接建立”） |
| `nl-assets` | 角色素材包的格式与校验，各端共用同一份实现 |
| `nl-node` | harness 节点本体：agent 循环、工具调用、记忆、子代理调度、远程存储服务 |

所有客户端都直接链接这些 crate，同一份逻辑、同一份测试。

### 物联网端

- 硬件：ESP32-S3（带 PSRAM，可做语音）。
- 固件：Rust + `esp-idf-svc`；语音唤醒与音频处理通过 FFI 调用 ESP-SR / ESP-ADF。
- 职责：传感、执行、音频采集与播放。不运行 LLM，语音识别与合成、存储、子代理都交给远端节点。
- 连接：只尝试两种方式——局域网直连附近的节点，或通过 WebSocket / MQTT 连接网关中继。不做 NAT 打洞。

### 桌面端

桌面端是一个 Tauri 2 应用，前端用 TypeScript，后端是 Rust：

| 组成 | 职责 |
|---|---|
| 主窗口 | 聊天、设置、记忆管理，也会显示角色 |
| 桌宠窗口 | 透明、无边框、置顶、不占任务栏，只显示角色，可拖动 |
| 内嵌 `nl-node`（待实现） | 在 Tauri 后端进程里运行本机的 harness 节点；托盘、开机自启使用 Tauri 官方插件 |

关掉主窗口后桌宠仍留在桌面上，两个窗口都关闭后应用退出。

选择 Tauri 而不是 Flutter 桌面版的原因：

- 主窗口也要显示角色。Flutter 桌面版在 Windows / Linux 上嵌入的 WebView 会浮在 Flutter 控件之上，而 Tauri 的界面本身就是 Web，主窗口和桌宠直接共用 `web/stage` 渲染页。
- Rust 核心与界面在同一个进程里，不需要跨语言桥接。
- 多窗口、透明窗口、点击穿透、托盘、开机自启、全局快捷键、自动更新都有官方支持；Flutter 桌面版的多窗口 API 仍是实验性的，其余能力多依赖社区插件。

代价是桌面（Web）与移动端（Flutter）各有一套界面，视觉一致靠同一份设计规范和共用的角色渲染页保证。另外，macOS 上的透明窗口需要开启私有 API，因此桌面版无法上架 Mac App Store；Linux 上的 WebKitGTK 渲染能力也较弱。

桌宠需要逐像素点击穿透：鼠标落在角色上时响应，落在透明区域时穿透到下面的程序。Linux Wayland 拿不到全局光标位置，需要改用 input region 单独适配。

### 移动端

- Flutter，Rust 核心通过 `flutter_rust_bridge` v2 接入。
- 推送、BLE（给 ESP32 配网）、来电式界面、前台服务优先使用成熟插件，不够时直接写 Kotlin / Swift 平台代码。
- 移动端是“间歇在线”的轻节点：运行 Rust 核心（协议、传输、加密、本地缓存），不运行完整的 agent 循环。iOS 不允许后台常驻连接，所以角色主动发消息要由网关通过 APNs / FCM 推送唤醒。

### 云端 harness 节点

与桌面端是同一个 `nl-node` 二进制（tokio + axum），通过编译特性启用更多能力：

- agent 循环与 LLM provider 抽象；
- MCP 工具接入，扩展脚本走 MCP 或 WASM 沙箱；
- 长期记忆（SQLite + 向量索引）；
- 子代理调度；
- 为单片机等存储有限的设备提供远程文件服务。

### 云端总网关

- Rust（axum）+ PostgreSQL + Redis（在线状态）。
- 登录：OIDC；设备通过配对码换取短期 token。
- API key：信封加密保存，由网关代为调用模型，或签发权限受限的短期凭证。
- 推送：向移动端发送 APNs / FCM 推送。
- 互联与中继：协助节点建立直连，全部失败时负责中继。

## 连接建立

两个节点之间按以下顺序尝试，前一种失败才尝试下一种：

1. 局域网直连（mDNS 发现）；
2. 公网 IPv6 或公网 IP 直连；
3. UPnP / NAT-PMP 端口映射；
4. STUN UDP 打洞；
5. 网关中继。

Rust 节点之间候选方案是 iroh（基于 QUIC，内置直连、打洞和可自建的中继），备选是 WebRTC（str0m / webrtc-rs）加 coturn，最终选择待评估。无论走哪条路径，会话层都做端到端加密（例如 Noise 协议）。

## 角色形象与素材包

角色形象由 `web/stage` 渲染页负责：桌面端的主窗口和桌宠窗口直接引用它，移动端通过 `webview_flutter` 嵌入，各端共用同一个渲染页和同一套包格式。

**Live2D 不进仓库。** Cubism Core 是 Live2D 的专有软件，不能随开源仓库分发，因此 Live2D 的运行库和模型都以独立素材包提供：

| 包类型 | 内容 | 校验 |
|---|---|---|
| runtime 包 | Cubism Core、Cubism Web Framework、shader 及其许可文件 | 每个版本的 NL 写死一个运行库摘要，对不上就拒绝加载 |
| character 包 | 模型、贴图、动作、音频、`character.json` | 只允许数据文件（扩展名白名单），校验文件头、引用完整性和大小上限 |

- runtime 包与 character 包分开，用户分享角色时不会连带再分发 Cubism Core。
- 用户导入的包无法向渲染页注入代码：代码只能来自摘要匹配的 runtime 包。
- `character.json` 记录作者、许可和来源，界面中原样展示。
- 素材包按内容哈希存放在 `nl-node` 或网关的存储中，各端按需拉取。
- 没有 runtime 包时，退回其他形象格式或静态图片。

## 测试策略

项目规定没有测试的代码不能合入，各端的测试方式如下：

| 端 | 方式 |
|---|---|
| 共享核心与节点 | `cargo test`，协议编解码、素材包校验等逻辑全覆盖 |
| 物联网端 | 业务逻辑在主机上做单元测试，固件在 QEMU / Wokwi 模拟器中运行；需要真机验证的部分在 PR 中写明 |
| 移动端（Flutter） | widget test 与 golden test（截图对比），可在 Linux 上无头运行 |
| 桌面端（Tauri） | 前端逻辑用 vitest，Rust 后端用 `cargo test`；CI 在三个系统上构建安装包；窗口透明、拖动、穿透需在各平台手动验证并记录 |
| 连接建立 | 在模拟 NAT 环境中做集成测试，覆盖每一级回退 |
| iOS | 在 macOS CI runner 的模拟器上运行 |
