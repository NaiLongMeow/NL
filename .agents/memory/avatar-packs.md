The desktop pet has two modes that the user picks: **light**, the built-in ball or an avatar of the user's own, made of code (a page of the pack's own, run sandboxed; shown first) or of images, and **Live2D**, an avatar's Live2D model. Users add avatars themselves, as folders with an `avatar.json` in the format published with the agent skill [skills/nl-avatar](../../skills/nl-avatar/SKILL.md) (spec: `references/format.md`), usually by asking an agent such as Claude Code or Codex to convert their art, check it, and install it. Live2D never enters the repository, and NL never ships the Cubism runtime.

Each rule has one implementation that every reader shares:

- **File rules** (allowed extensions, file count and size limits) are `skills/nl-avatar/scripts/lib/rules.json`, read by the skill's checker and, through `include_str!`, by the Rust crate `nl-assets`, which is the app's security boundary: the desktop serves a file over the `nlavatar` URI scheme only when its path passes the file rules, and never follows a link out of a pack folder.
- **Manifest rules** (keys, the cue mapping and its fallbacks, referenced files, Live2D names) are `skills/nl-avatar/scripts/lib/format.ts`, imported by the skill's CLI, the desktop main window, and `web/stage`. The skill runs on Node 22.18+ type stripping, so the skill's files stay erasable TypeScript with `.ts` import extensions.
- **The code rendition's sandbox** *(user, 2026-11-19: importing code is the freest way, and it runs sandboxed)* has four parts, each covering what the others cannot: the frame's `sandbox="allow-scripts"` and nothing more (web/stage/src/code.ts), which gives the page an opaque origin; `pack_policy`, the content-security policy served with every pack file, which lets the page load only its own pack's files (apps/desktop/src-tauri/src/avatars.rs); the windows' own policy (tauri.conf.json), whose `frame-src` admits only pack files and whose `script-src` admits only the Live2D runtime's folder; and `sandbox-frames.js`, run in every frame, which deletes the WebRTC constructors in frames with an opaque origin, since no content-security policy covers WebRTC. The page says it is ready and then hears the cues as messages (format.md, "The code rendition"). On Windows, Tauri adds its scripts to every frame, so the frame has `__TAURI_INTERNALS__` and `window.ipc`; IPC still fails there only because the pack policy blocks the fetch to `ipc.localhost` and the fallback, `chrome.webview.postMessage` from a frame, raises that frame's own `WebMessageReceived`, which wry 0.57 does not handle. A wry that handled frames' messages would open IPC to the frame.
- **The Live2D runtime**: release builds load one only if its digest is in `ACCEPTED_RUNTIMES` (apps/desktop/src-tauri/src/avatars.rs), which is empty, so released builds show no Live2D. Debug builds take a runtime from `NL_DEV_LIVE2D_RUNTIME` and extra avatar folders from `NL_DEV_AVATARS`.

**Why:**

- Users import avatars through agents, so the spec and its checker must be something an agent can install and run by itself (a skill with a CLI), and the app must accept exactly what the checker accepts; one rules file read by both keeps them from drifting apart.
- Avatars come from anyone, so nothing in a pack runs with the app's rights (T8). Images and models are data; a code rendition runs only in the sandbox above, which the user chose over full access on 2026-11-19.
- The sandbox has one known gap that no content-security policy or browser setting closes: a frame the page points at an address it may not load (a nested frame, or its own navigation) is blocked before any request, but WebView2 first resolves the name and opens a TCP connection to it, a slow one-way channel out. Closing it needs the network layer (the pet window in a WebView2 environment of its own behind a refusing proxy), which costs another browser process and the storage the pet shares with the main window; that is the user's decision (UI design note, question 17), and the user docs say meanwhile to install code avatars only from people the user trusts.
- Cubism Core is under the Live2D Proprietary Software License and cannot be redistributed with an open-source repository; the Cubism Web Framework is under Live2D's own Open Software License. Both load at run time from a runtime folder, never from an avatar, so sharing an avatar never redistributes them.
- An app that loads any user's model is a Live2D "Expandable Application". Every publisher, individuals and General Users included, needs Live2D's approval and a special agreement before release; "as a general rule, fully free of charge is not eligible for approval"; General Users pay a revenue share of $1.88 (¥300) per sale or 20%, whichever is higher. Whether and how released builds show Live2D is therefore the user's decision (UI design note, open question 13; roadmap, open question 1). The terms do not say whether an app whose users bring their own runtime still counts as one; ask Live2D before relying on that.

**How to apply:**

- Never commit `.moc3` files, `*.model3.json`, Cubism Core or Framework builds, art without a recorded license, or pack archives; gitignore any place where a pack is staged. Test fixtures are generated at test time by `skills/nl-avatar/tests/fixtures.ts`.
- Change file rules only in `rules.json` and manifest rules only in `format.ts` together with `references/format.md`, then run the tests of the skill, `web/stage`, the desktop app, and `nl-assets`.
- Do not add an accepted runtime digest, or describe a way for released builds to load Live2D, without the user's decision.
- Show the author and license from `avatar.json` beside the avatar.
- Change the sandbox's parts together, and after any change to one of them (the frame's `sandbox` attribute, `pack_policy`, the windows' `frame-src` or `script-src`, `sandbox-frames.js`, the IPC or init-script behavior of a Tauri or wry upgrade) run the real-app probe again: a code pack that tries every way out, a local sink that counts TCP connections, HTTP requests, and UDP datagrams and proves it is listening before and after, and a positive control. Run it in a build with the release policy (`pnpm tauri build --debug --no-bundle`): development pages come from the dev server, where the windows' `frame-src` is not in force.

- The user's decisions: 2026-11-15, Live2D stays out of the repository and runtimes ship apart from characters; 2026-11-19, "设计为双模式可选，一种是低占用的小球或自定义桌宠，一种是占用性能多的live2d，用户可自行导入形象，可以设计一套规范并做成skill，这样就能确保用户可以轻松导入，因为一般都会让agent如ClaudeCode、Codex自动帮忙配置".
- Live2D's Expandable Application terms, https://www.live2d.com/en/sdk/license/expandable/, read 2026-11-19; the Cubism Core license from Live2D's EULA pages, read 2026-11-15.
- The first design followed dsh-go (gitignored `.ref/dsh-go`, AGPL, read for ideas only): `app/lib/companion/companion_pack.dart` and `docs/design/companion.md` §3, read 2026-11-15. dsh-go bundles runtime and character in one zip; keeping them apart is NL's own choice.
- Checked in the running development app on 2026-11-19: the app lists installed and development avatars, and the pet shows a different look for each state in both the light and the Live2D rendition.
- The user's choice of a sandbox for code avatars, 2026-11-19 ("沙箱运行 (Recommended)"), after asking for code import as the freest way ("1.代码导入，最自由，本质是注入代码").
- The sandbox probe on 2026-11-19, in the development build and in a debug build with the release policy, Windows 11, WebView2, over the DevTools protocol with no global input: invoke timed out with no response in any page (nothing reached Rust); fetch, images, beacons, WebSocket, EventSource, WebTransport, CSS urls, imports, scripts, frames, prefetch, worker fetches, pings, forms, popups, dialogs, top navigation, storage, cookies, IndexedDB, Cache Storage, service workers, other packs, and the runtime were all refused; WebRTC was undefined in the frame and in its srcdoc and `javascript:` children, and no STUN or TURN reached the sink while the positive control from the pet page did; with the release policy the frame's own navigation sent no request, and Live2D still loaded under the narrowed `script-src`; the frame is transparent on screen in light and dark color schemes. Blocked frame navigations opened one TCP connection per new address and sent nothing, as reported in suredo/Tessera#72; WebRTC's escape from CSP is reported in daintreehq/daintree#15816 and backnotprop/plannotator#1844.
