Vitest and the Vite page in a browser do not show what the desktop app does: outside Tauri, `inDesktopApp()` is false, so custom themes, the caption color, and the title bar insets are absent. Ways to check the real app on Windows:

- **Drive the app's own page.** Start it with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` in the environment (`pnpm tauri dev`, or the release exe). `http://127.0.0.1:9222/json` then lists the main and pet pages, and any Chrome DevTools Protocol client (Node's built-in WebSocket is enough) can evaluate script in them, including `window.__TAURI_INTERNALS__.invoke(...)` to call the app's commands. The main page is `http://localhost:1420/` in development and `http://tauri.localhost/` in a release build. Never ship or document the flag as a user setting: it opens the page to any local process.
- **Clicks and typing without global input.** Over the same connection, `Input.dispatchMouseEvent` (right button included, which opens the page's context menus), `Input.insertText`, and `Input.dispatchKeyEvent` go to the page alone, so the foreground window and the user's keyboard are untouched; send `Emulation.setFocusEmulationEnabled` first, so that a window in the background behaves as focused. Find click targets inside the transcript column: a context menu's `display: contents` wrapper has an empty rectangle, and the live region for screen readers repeats the last message. Posting `WM_KEYDOWN` to the webview's window instead does not work while NL is in the background: the page never receives the key. Leave Copy unchecked against the system clipboard, which holds the user's own content.
- **The title bar.** The tauri-custom-titlebar skill's `scripts/verify_windows_titlebar.py "NL"` checks hit-testing, hover, the resize band, and maximize; it moves the real mouse for about 15 s, so warn the user first. It does not check colors.
- **Colors behind the caption buttons.** Screen-grab the window (Pillow `ImageGrab`, per-monitor DPI aware) at the rectangle from `DwmGetWindowAttribute(DWMWA_CAPTION_BUTTON_BOUNDS)`, which is relative to the window rect, and compare with the bar beside it. Bring the window forward with `AttachThreadInput` and `SetForegroundWindow` rather than injected keys, and sample active and inactive.
- **A page's content-security policy.** DevTools' `Runtime.evaluate` is exempt from it (`new Function` runs there under a policy without `'unsafe-eval'`), so test a policy with what the page itself would do: append an inline `<script>` element, and fetch a local sink. Development pages come from the Vite server and are not under the windows' policy: the frame of a code avatar could navigate anywhere there. `pnpm tauri build --debug --no-bundle` gives a build with the release policy that still reads the development variables.
- **Network sinks.** To prove that nothing leaves a page, count arrivals at a local sink (TCP connections when accepted, HTTP request lines, UDP datagrams), make it exit when it cannot bind its ports, and send it a request and a datagram before and after each run: on 2026-11-19 a sink whose ports were still held by its predecessor logged "up" and heard nothing, which looked like a pass until a positive control failed. On Windows `SO_REUSEADDR` lets a second process bind a port already in use, so leave it off.
- **Frames.** A frame from another site runs in its own process: `Target.setAutoAttach` with `flatten` gives a session for it, and the parent's `Page.getFrameTree` does not list it. A DevTools screenshot paints such a frame white even when it is transparent; check transparency by giving the page an opaque color and capturing the window's pixels from the screen. In development, React's StrictMode mounts effects twice, so a renderer's first frame may be torn down at once: take the newest session.
- **Main-thread load.** Over the same debugging connection, send `Performance.enable`, then `Performance.getMetrics` twice some seconds apart: the growth of `TaskDuration` (in seconds) over the interval is the page's main-thread load. Inject a style that sets `animation: none` on one group of elements at a time to see what each costs. A development build costs more than a release build, so compare like with like.
- **When the app hangs.** `tasklist /v` marks it Not Responding, and `Get-Process nl-desktop` lists each thread's CPU time; the main thread is the process's first thread. Its stack can be sampled without a debugger through dbghelp.dll (`SuspendThread`, `GetThreadContext`, `StackWalk64`, `SymFromAddrW`; the debug build's PDB is in target/debug), for example from Python with ctypes.
- **Browser keys.** Every build turns them off, development builds too unless started with `NL_DEV_BROWSER_KEYS=1` (user, 2026-11-19). Checking a release build: `pnpm tauri build --no-bundle` in apps/desktop gives `target/release/nl-desktop.exe`. Send keys with `SendInput` only while NL is the foreground window, and prove each key arrived (a capturing `keydown` listener) before taking "nothing happened" as a pass.

**Which Windows.** Read the version from WMI (`(Get-CimInstance Win32_OperatingSystem).Caption`, `BuildNumber`) or `ver`: the registry's `ProductName` says Windows 10 on Windows 11 too. Records before 2026-11-19 wrongly called the maintainer's Windows 11 machine Windows 10.

**Evidence:** Driving the page, the title bar script, caption sampling, and the browser keys were used on 2026-11-19 on Windows 11 build 26300 (26H2) at 150% scale: the verify script printed ALL PASS; the caption matched the bar in light, dark, and custom themes; the release build ignored F5, Ctrl+R, Ctrl+Shift+R, Alt+Left, F12, Ctrl+Shift+I, Ctrl+P, Ctrl+F, and Ctrl+plus while each key reached the page. Windows 10 has not been tried, so the system-caption fallback in src-tauri/src/caption.rs is unverified. Clicks and typing over the debugging connection checked the context menus, quoting, editing, versions, rewinding, the session settings dialog, and branching in the development build the same day, with the window in the background. The policy, sink, and frame notes come from the code-avatar sandbox probe of the same day ([[avatar-packs]]). The main-thread measurement was used the same day on the pet and the main window, and a probe page showed CSS animations of SVG groups costing about ten times the same transform and opacity animations on HTML elements. The same day `ver` and WMI reported build 26300 and the Caption "Microsoft Windows 11", installed 2026-06-29, while the registry's ProductName read "Windows 10 Pro".

On 2026-11-19 the app froze after the ball's layers became animated HTML boxes inside the title bar: the main thread's stack sat in WebView2's window procedure, in `NtUserSetWindowPos`, because WebView2 keeps the drag region (`app-region`, which is inherited) as child windows of the app's main thread and rebuilt it on every frame. Making the boxes inside the bar `app-region: initial` took that thread from 172 to 0 ms of CPU a second (apps/desktop/src/app/TitleBar.module.css).

**Recheck when:** Tauri or wry is upgraded (rerun the verify script), WebView2 stops reading the environment variable, or the app's development or release origin changes.
