These rules hold in every stage of [the roadmap](../plan/roadmap.md). A change that breaks one is wrong even if it works and its tests pass. If a task cannot be done without breaking one, stop and ask the user. Cite rules by id ("S2", "M2") in design notes, pull requests, and reviews. The terms are defined in [[product-direction]]; how sessions, memory, and compacts work together is explained in [[distributed-design]].

## Contracts

- **P1 Contracts first.** Ends meet only through contracts specified in the repository: the gateway's API (sign-in, enrollment, the model proxy, the shared file system, notices, the capability registry and remote calls) and the messages under `proto/`. A feature that involves two ends starts with the contract change and its tests. The shared Rust crates are a convenience for our own ends, not the contract. *Why:* any end must stay replaceable, including by other people's code in another language.
- **P2 One harness core, one interface.** Every node runs the same harness core: the turn loop, the session record, memory access, forks, compaction. Each platform's shell (Tauri, Flutter, ESP-IDF, the command line) drives the core through the same interface. No platform gets private features in its shell. *Why:* a feature built once must work on every node.
- **P3 Capabilities, not device types.** A node declares what it can do, and work is routed by capability. Code never asks whether a peer is an ESP32, a phone, or a desktop. A node that lacks an ability calls it on a remote node (S8).
- **P4 Additive evolution.** Never change or reuse a field number, never change a field's type or meaning, and never change what an existing API call does. Add fields and calls, mark removed ones reserved, and make receivers ignore what they do not know. Until the roadmap declares the contracts frozen, a breaking change is allowed only as a deliberate decision in its own pull request (for `proto/`, with the `buf skip breaking` label), never as a side effect of other work.
- **P5 The lifeline never breaks.** From the first release that ships firmware, everything an old device needs to sign in to the gateway and fetch an update stays backward compatible for good. *Why:* a device left in a drawer for a year must still be updatable.
- **P6 Sized for the smallest node.** The harness core runs on an ESP32, so its required path (sign in, read memory, build a prompt, stream a reply, append to the record) works in bounded memory with streaming input and output. A node with little storage keeps little and reads the rest through the gateway. What a small node cannot do locally, it calls remotely.
- **P7 Streamable and cancellable.** Replies stream. Every long operation can be cancelled. The user interrupting (starting to talk, pressing stop) is a normal event, not an error path.
- **P8 Cues are semantic.** The harness emits what the character expresses (an emotion, listening, thinking, speaking, a gesture), never renderer commands such as a motion file name or a servo angle. Each shell maps cues to what it has: sprites, a 3D model, LEDs, a servo. Which avatar formats a character pack carries is decided when the character stage starts (user decision, 2026-11-16); until then the cue interface must not assume any one format.

## Distribution and state

- **S1 Execution is distributed; memory is central.** The harness loop, sessions, tools, and devices live on nodes. Accounts, keys, the shared file system, notices, and the capability registry live behind the gateway. A node holds caches of shared state, so losing a node loses only its local transcripts.
- **S2 Sessions are local and separate.** A session runs on one node. Its JSONL, one event per line, is that node's local record, holds far more than the conversation, and is not synchronized; it leaves the node only by deliberate upload. A node may run several sessions at once, and sessions may run on several nodes at once: that is the character splitting. No node depends on another node's transcript.
- **S3 Memory is files in the shared file system.** There is one shared file system per account. Every node reads and writes the same files through the gateway. Compacts live there in a read-only folder: the system writes them, and the harness can read and search them. Indexes and caches built from these files are derived and can be rebuilt.
- **S4 Urgent now, the rest at a pause.** Urgent memory is written at once, pushed to every running node, and appended to their running sessions as a notice addressed to the harness, not to the user. Normal memory waits until a stretch of conversation stops: a separate judgment decides whether anything needs remembering, an organizing fork does the work, its core content returns to the main agent, and other running sessions receive a digest at their next turn.
- **S5 Compacts carry a conversation.** A session is compacted when it reaches the context limit and automatically when it is closed. The compact made at close is uploaded to the read-only folder. The gateway keeps the last request of every session, and when a node goes away without closing, the gateway appends the compact prompt itself. Carrying on from another node means starting a session there from a compact and the shared memory.
- **S6 Accounts are sealed.** One account is one user and one character. Every stored item and every message belongs to exactly one account, and no interface lets data, memory, notices, or keys cross from one account to another. Tests prove it. *Why:* this is what signing in is for.
- **S7 The gateway is the one required service.** Every node signs in through it. With a gateway account, any single node is a complete companion: the desktop app, a phone, or an ESP32 on its own. Other nodes are additions. A missing optional part degrades a feature with a clear message; it never breaks the product.
- **S8 Remote capabilities come in two sizes.** A tool call is short and answered at once. A task is a remote sub-agent: the remote node runs it in a session of its own and returns a result. Weak hardware, and phones whose background work gets killed, use these instead of doing the work locally. Calls go through the gateway first; direct routes between nodes are an optimization added last.
- **S9 Data formats are promises.** Once a release has written user data (session JSONL, memory files, compacts, packs, configuration), every later release reads it or migrates it automatically, and the migration has a test. Never ask the user to start over, and never drop data silently. The user can always export and delete their data.

## Model and prompts

- **M1 Prompts are English.** Every system prompt, tool description, notice, and fork instruction is written in English. The system prompt states which language the character replies in, as Claude Code's prompts do. Prompt design learns from Claude's ([[reference-designs]]).
- **M2 The prefix never changes.** Within a session the prompt only grows at the end. Its order is: system prompt, tool definitions, the memory snapshot taken when the session started, the conversation, and notices appended as they arrive. Nothing already sent is edited, reordered, or removed, and nothing that varies (a clock, a random id) appears early in the prompt. New information is appended as a notice. Only compaction starts a new prefix. *Why:* the provider's prefix cache is what makes a long-running companion affordable.
- **M3 Only history lines form the prompt.** Each JSONL line says whether it is part of the history. Judgments, fork records, usage figures, and other bookkeeping are records only and never enter the prompt.
- **M4 Forks reuse the parent's prefix.** Work that needs the whole conversation runs as a fork: the parent's exact prompt plus one appended instruction, so that it hits the cache and runs beside the main agent without stopping it. The memory judgment, the organizing fork, and the compact are forks. Only one organizing fork runs at a time, and a fork hands back only its core content, as an appended notice.

## Trust and security

- **T1 The gateway is trusted, and the docs say so.** It signs users in, holds the keys, calls the models, and stores each account's shared file system and each session's last request. Whoever runs a gateway can read what its accounts store. Users are protected by sealed accounts (S6), encrypted transport, secrets encrypted at rest, and the option to run their own gateway. Docs and UI never claim more than this.
- **T2 Every node signs in.** A node enrolls into an account and holds a credential for it that can be revoked at once. Every connection is authenticated and encrypted in transit: node to gateway, and node to node. Every enrollment is shown to the user on their other nodes.
- **T3 Keys stay in the gateway's vault.** API keys live only there, encrypted at rest. A key can be submitted and used, and can never be read back through any interface. A node reaches language models and speech services through the gateway's model proxy. Keys never appear in the repository, logs, messages, node storage, or crash reports.
- **T4 No home-made cryptography.** Use established protocols and audited libraries. The design of sign-in, enrollment, credentials, and what a node's credential allows is a reserved decision.
- **T5 Nothing listens unauthenticated.** The default bind address is loopback. Every listening socket requires authentication, loopback included, because other local programs and web pages can reach loopback. The exceptions are a health probe that reveals only liveness and version, and the gateway's sign-in endpoints, which exist to authenticate and are rate-limited.
- **T6 All input is hostile until validated.** This covers network frames, packs, files, tool results, sensor values, and model output. Parsers enforce size limits and have fuzz or property tests. Text from tools, files, the web, or other people reaches the model marked as untrusted data and is never merged into system instructions. Model output is data and is never executed.
- **T7 The model proposes, policy decides.** Actions that touch the physical world, spend money, contact other people, or delete data pass a policy check outside the model (allow-lists, limits, confirmation). A remote call obeys the policy of the node that carries it out. A device enforces its own safe ranges locally and returns to a safe state when it loses its connection.
- **T8 Imported content carries no code.** Character packs are data only. Code reaches a renderer or node only from a signed release, a digest-pinned runtime pack, or a tool the user installed and approved. Tools are MCP servers: separate processes or remote services, never code loaded into the node process; loading third-party code into the node, by any mechanism, is a reserved decision. Firmware accepts only signed images and can roll back a bad one.
- **T9 Content stays out of logs.** By default, logs, traces, metrics, and crash reports hold no conversation text, audio, memory text, or secrets, on nodes and on the gateway alike. Nothing is reported off the user's machines or the gateway unless its owner opts in.
- **T10 Memory has provenance.** Each memory records where it came from: the user said it, the character inferred it, or a tool returned it. Content from tools or the web never becomes a memory without that label.

## Engineering

- **E1 Logic without I/O.** The harness core, connection policy, audio logic, and pack validation are state machines or pure functions driven by events. Sockets, audio hardware, HTTP calls, clocks, and storage sit behind interfaces at the edges. The core compiles for every node, the ESP32 included, so it depends on no particular async runtime or operating system. Firmware and UI code are thin shells over crates tested on the host. *Why:* this lets agents test without hardware or paid services, and lets a library or a whole end be replaced.
- **E2 Every external thing has a fake.** The language model, speech services, the gateway, the clock, and remote nodes each have a deterministic fake for tests. CI needs no secrets, no hardware, and no access to providers. The harness core is tested on the host for every kind of node.
- **E3 Sessions can be replayed.** A session can be replayed from its JSONL in a test. A bug report should become a replay test before it becomes a fix.
- **E4 Few moving parts.** A node is one binary or library that keeps plain files, with SQLite at most for derived data. The gateway is one binary backed by PostgreSQL and Redis, which are its only required external services. Making anything else required (a broker, an object store, a second database) is a reserved decision. Tests use disposable PostgreSQL and Redis instances, never one that holds real data.
- **E5 DeepSeek first, behind interfaces.** Language models, search, fetch, speech recognition, and speech synthesis sit behind interfaces, each with its DeepSeek adapter and a fake ([[deepseek-reference-provider]]). Other adapters are added when someone needs them, and nothing rules out a local, offline one. No vendor's proprietary API is hard-wired into the turn loop. The harness is sized for a small, fast main model: few tools and plain instructions.
- **E6 The operator chooses the endpoints.** Whoever deploys a gateway runs it and decides which networks and services it relies on. So nothing is hard-wired: every infrastructure endpoint (model and speech providers, push, update source, rendezvous) is configurable, and the parts NL ships can be self-hosted.
- **E7 Budgets are acceptance criteria.** The roadmap lists budgets for latency, memory, flash, idle CPU, and network use; a change that breaks one is a regression. Every autonomous loop (proactive contact, routines, forks, retries, tasks) has a spending limit and a stop condition, and the user can see what was spent.
- **E8 Dependencies are deliberate.** Prefer mature, permissively licensed crates. No GPL, AGPL, or proprietary code is linked into what NL ships. Name and justify each new dependency in the pull request. Before calling a library or a provider API, read the documentation of the version in use; do not write calls from memory.
- **E9 Small, complete slices.** One pull request does one thing, with its tests and doc changes, and leaves main releasable. Work that belongs to a later stage gets a seam (an interface and a fake) and a TODO entry, not a half-built feature and not a stub that pretends to work. Tests, lints, and CI gates are never weakened to get a change through.

## Reserved decisions

An implementer does not take these alone. Write a short design note under `docs/design/` and get the user's approval first.

1. Anything in T1 to T4: sign-in and enrollment, credentials and what they allow, key storage, transport security.
2. A breaking change to a contract (P1), and any new kind of shared state or new way for state to move between nodes (S1 to S5, S8).
3. The format of user data after its first release, and any migration of it (S9).
4. The prompt layout and the fork mechanism (M2 to M4).
5. A new deployable component, programming language, required external service, or UI framework.
6. Anything with licensing weight: bundled assets, a non-permissive dependency, a proprietary SDK.
7. Enabling by default anything that acts on the physical world, spends money, or contacts other people.
8. Repository settings, rulesets, release signing, and store publishing.
9. Relaxing or removing a rule in this file, or a non-goal or product rule in [[product-direction]].

For everything else, choose the smallest design that meets the current stage's exit criteria, say what you chose in the pull request, and record it in memory only if a later session would decide differently without it.

**Why:** These are the properties that are cheap to keep from the first commit and close to impossible to add later: what the contracts are, where state lives and how it moves, a prompt layout the cache can follow, who is trusted with what, and whether the code can be tested without hardware or paid services. The project is built mostly by agents that each see one task, so a rule that is not written here will be broken by a change that looks reasonable locally.

**How to apply:** Check a design against the five groups before writing code and again in review. docs/architecture.md and the READMEs were written before these rules and disagree with them in many places (end-to-end encryption against the gateway, an ESP32 that only handles audio, a phone that runs no agent loop, MQTT, a WASM sandbox). This file is newer: follow it. Rewriting those docs is its own item in TODO.md (Stage 0); do not rewrite them inside an unrelated change.

**Evidence:** The user's decisions of 2026-11-15 in docs/architecture.md, [[live2d-asset-packs]], [[client-stack-decision]], and [[tech-choice-criteria]] (protocol first, keys only in the gateway, PostgreSQL and Redis behind the gateway, agent-operable toolchains). On 2026-11-16 the user delegated the direction to the agent and then corrected its first drafts in discussion: the gateway is the trusted login system (S7, T1 to T3); every node runs the harness (P2, P6, S1); sessions are local JSONL and separate while memory is shared files (S2, S3); urgent and normal memory, forks, and compacts work as in S4, S5, and M4; accounts are sealed (S6); remote capabilities are tool calls and tasks, through the gateway first (S8); prompts are English with a stable prefix (M1, M2); DeepSeek is the first provider (E5). The user also decided that whoever deploys a gateway runs it and chooses what it depends on (E6), and that avatar formats are chosen when the character stage starts (P8). The remaining rules are the agent's and the user may overrule them.

**Recheck when:** A stage's design note shows that a rule cannot hold; the contracts are frozen (P4 then allows additive changes only); or DeepSeek's prefix cache turns out to behave differently from what M2 and M4 assume.
